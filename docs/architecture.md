# 設計と拡張時の契約

## 現在の処理経路

USB UVCカメラ → HALの3スロットコピー → ハードウェアJPEG復号 → 画面プレビュー、
および同じフレームのH.264エンコード → RTSP配信。推論は行いません。

HALは復号やスケーリングを行わず、生フレームのコピーと世代管理だけを担います。
消費者はフレームの取得時刻 `captured_us` を見て、自分で鮮度を判断します。
古いフレームを最新として表示しません。

## Tab5のライブカメラアダプタ

LVGLロック、RTSPタスク、割り込みの中で復号や変換を行いません。
プレビューは最新フレームのみを扱い、古いフレームは捨てます。キューを無制限に増やしません。

UVCはアプリケーションの生存期間中に所有し、RTSPのTEARDOWNではキャプチャを止めません。
MIPIフォールバックはありません。

プレビューはUVCの生バッファを借用しませんが、RTSPが復号済みのRGB888は借用します。
ハードウェアJPEGエンジンが1基しかなく、同じフレームを二重に復号するとエンジンが飽和して
画面が数秒ごとに黒転落したためです。借用はミューテックスで保護し、コピーを取ったら即座に解放します。
借用を保持したまま `bsp_display_lock()` を待つと、RTSPの次の復号が止まります。
詳細は `docs/usb_rtsp.md` の「ハードウェアJPEGデコーダの共有」を参照します。

## コア割り当て

`hal_uvc.cpp` がCPU1をカメラ経路に確保します。UVCドライバタスク（優先度6）、
`uvc_stream`（5）、`uvc_render`（4）がCPU1固定です。RTSPタスクはCPU0に固定します。
プレビューは固定せず、優先度3で動かします。

`CONFIG_FREERTOS_HZ` は100なので `pdMS_TO_TICKS()` は10ms未満をすべて0ティックに丸めます。
`vTaskDelay(0)` は同一以上の優先度にしかCPUを渡さないため、10ms未満の待機はビジーループになります。
RTSPタスクでは `rtsp_delay_ms()` が最低1ティックを保証します。
周期実行には `xTaskDelayUntil()` を使います。`vTaskDelay()` は処理時間の後に待つため、
処理が重いと実周期が伸びます。
