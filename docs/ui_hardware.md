# Camera Clock画面と実機受入

ネイティブ縦画面は720x1280です。上部720x640にアスペクト比を保ったUSB映像、下部の濃紺/水色パネルに
ローカル時刻とUSB接続状態を表示します。カメラが切断または古くなるとプレビューを消します。
プレビューは約5Hzの消費者で、UVCの生バッファは借用しません。RTSPが復号済みのRGB888は借用します
（`docs/usb_rtsp.md` の「ハードウェアJPEGデコーダの共有」）。

レイアウト、色、生成済みフォント `camera_clock_font_64.c` と `camera_clock_time_88.c` は
`tab5_rtsp_logger` revision `e5e5fee79c2232bd5de4a994d8f90e12f4630952` の
`app/apps/app_baby_logger` から移植しました。上流MIT通知は
`licenses/tab5_rtsp_logger-MIT.txt` に保持します。ランチャー、保存、Home Assistantアプリケーション全体は移植しません。
固定した上流BSPがLCD識別、タッチ、2つのIO expanderを処理します。

タイムゾーンは `CONFIG_EDGE_TIMEZONE`（既定 `JST-9`）で、UIより先に `edge_clock_init()` が適用します。
Wi-Fi接続後に適用していたときは、ソフトリセット後にRTC時刻が残るため、UTCのまま9時間ズレた時刻を表示していました。
SNTPクライアントは常駐し `CONFIG_EDGE_SNTP_RESYNC_MINUTES`（既定60分）ごとに再同期します。
1回だけ同期して停止する構成では、ESP32-P4のRTCドリフトを長時間運転中に補正できません。
同期待ちの時計はプレースホルダを表示し、状態パネルの `CLOCK //` 行が `UNSET` / `RTC-ONLY` / `NTP` を明示します。
`camera_clock_font_64.c` と `camera_clock_time_88.c` は `--symbols /:0123456789` で生成されており `-` のグリフを持ちません。
旧プレースホルダ `----/--/--` と `--:--:--` はLVGLの欠字ボックスで描画され、これが起動直後の文字化けでした。
プレースホルダは `0000/00/00` と `00:00:00` に変更し、フォントが持つグリフだけで構成します。
代わりに48pxのmontserratを追加リンクする方式は、イメージが324KiB増えPSRAM空きが96KiB減るため採用しません。
RTSPの2MiB連続バッファと同居できる余裕がありません。曜日ラベルはmontserratなので `(--)` を使えます。
オフラインRTC初期化は未移植です。

## コア割り当てと待機

`hal_uvc.cpp` はCPU1をカメラ経路に確保しています。UVCドライバタスク（優先度6）、`uvc_stream`（5）、
`uvc_render`（4）がCPU1固定です。RTSPタスクはCPU0に固定し、ネットワークとエンコード処理をCPU1から外します。
`edge_ai` と `edge_preview` は固定しません。CPU1にはカメラタスクが3つ、いずれも両ワーカーより高い優先度で
載っているため、スケジューラに配置を任せます。

`CONFIG_FREERTOS_HZ` は100なので `pdMS_TO_TICKS()` は10ms未満をすべて0ティックに丸めます。
`vTaskDelay(0)` は同一以上の優先度にしかCPUを渡さないため、優先度5の `rtsp` タスクにあった
1〜5msの待機はビジーループとして働き、CPU0を100%占有してIDLE0とLVGLを飢餓状態にしていました。
`rtsp_delay_ms()` が最低1ティックの待機を保証します。

IDLE監視は両コアとも有効のまま、`CONFIG_ESP_TASK_WDT_TIMEOUT_S` を10秒にして、
重い1フレーム分の処理を吸収します。

USBのアイソクロナス転送で切り詰められたMJPEGフレームは、ハードウェアJPEGデコーダに渡す前に
`edge_jpeg_payload_is_complete()` でSOI/EOIを検査して除外します。不完全なフレームはデコーダを
タイムアウトまで待たせ、共有2D-DMAトランザクションを中途半端に解除します。

`CONFIG_ESP_SYSTEM_USE_EH_FRAME` は既定で無効です。RISC-Vでpanic時に実際のバックトレースを出せますが、
アンワインドテーブルでアプリが約780KiB大きくなり、`CONFIG_SPIRAM_XIP_FROM_PSRAM` によりその分がPSRAMから引かれます。
実測ではPSRAM空きが 2323036 → 1775308 バイトに減り、最大連続空きブロックがちょうど2MiBまで下がった結果、
RTSPの2MiB USB入力バッファが確保できずDESCRIBEが毎回失敗しました。panic調査時の使い捨てビルドでのみ有効にし、
RTSPを同時に動かすビルドでは有効にしないでください。

## 受入手順

1. ホストテストとIDFビルドを実行する。これは実機の証明ではない。
2. 正確なchip/MAC/ポートを識別し、置換前にflashを私有バックアップする。
3. アプリケーションSHA256、フラッシュ検証、起動/リセットのシリアルログを保存する。
4. 立会いで表示、色、向きを確認する。
5. 新しいUSBフレームとAI、プレビュー、RTSPが独立に動くことを確認する。
6. 私有映像を記録せずTCP RTSPをデコードし、少なくとも1回再接続する。
7. シリアルと復号ログを収集して、実時間で1時間以上動かす。復号フレーム、エラー、reset、heap傾向、条件を記録する。

flash backup、Wi-Fi設定、シリアルログ、カメラ画像はGit外に保管します。成功した長時間試験でもbaby検出精度や睡眠安全性は証明されません。
Scrypted/HomeKitと意図的なウォッチドッグ障害注入は独立した受入項目です。
